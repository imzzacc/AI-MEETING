# 测试与评测

分三层：自动化测试保证规则和一致性，本地端到端跑真实面试，模型评测衡量评分质量。前两层比较完整；第三层只在合成数据上做过，还谈不上验收。

## 1. 自动化测试

```bash
docker run -d --name ai-meeting-mongo -p 127.0.0.1:28029:27017 mongo:7.0
./mvnw -B -ntp clean verify                                   # 后端：单元测试 + 集成测试
python3 -m unittest discover -s scripts -p 'test_*.py'          # 评测脚本自身的指标计算
cd frontend && npm run check && npm run build                   # 前端：lint、类型检查、vitest
```

当前后端 185 个单元/服务测试和 16 个集成测试全部通过，前端 22 个测试文件全部通过。集成测试连接真实 MongoDB，连不上会直接失败，不会被跳过。CI 跑的也是这些命令。

自适应面试相关的测试：

| 测试类 | 覆盖内容 |
| --- | --- |
| `AdaptivePolicyTest` | 预算边界；为后续主问题预留时间；上限设为 0 时真正禁用追问；同一缺口不重复追问；后面主问题会考的知识点不提前追问；相同输入重放结果一致；伪造的引用不能变成“答错” |
| `AdaptiveInterviewServiceTest` | 重复请求只回放不重复计分；同 ID 不同内容拒绝；回答在调用模型前已经落盘；投影失败重试不重复加分；发布前预算变化会取消追问；刷新不重置计时；延期幂等且有上限；越权和超长回答拒绝 |
| `AdaptiveLiteFlowTest` | 真实 LiteFlow 链能跑通裁决 |
| `InterviewKnowledgeRetrievalTest` / `InterviewKnowledgeScopeTest` | 别名组匹配及近似负例；旧目录快照兼容；岗位/版本不匹配时只关闭受影响的主题 |
| `GroundedEvaluatorContractTest` | 工作流输出解析；旧格式和异常格式会明确失败；忽略模型给出的追问指令 |
| `GroundedFeedbackTest` | 证据被降级后，模型原来的肯定或否定结论不会留在反馈里 |
| `InterviewReviewServiceTest` | 报告重试不会重复写证据、不覆盖用户纠正；被移除的错题不会复活；重复练习不会刷掌握度；模型失败不记错 |
| `AdaptiveSessionDeletionTest` | 删除前校验归属；清理幂等；失败后由补偿重试；删除进行中的复习不会发布结果 |
| `AdaptivePersistenceIT` | 真实 Mongo 下，旧版本号写入被拒绝；并发提交只有一个成功；分页不越过用户边界；错题身份唯一 |

### 故障注入

`FaultInjectionHarness` 把真实的 `AdaptiveInterviewService` 接上可以出故障的存储、模型和 Redis 投影，能在任意一步让“进程退出”（抛出一个业务代码里 `catch (Exception)` 接不住的 `Error`），然后像客户端一样重试。

| 测试类 | 覆盖内容 |
| --- | --- |
| `AnswerCrashMatrixTest` / `AnswerCrashMatrixIT` | 设计文档 7.3 节的 8 个崩溃点逐个注入。重试之后和没崩溃的运行对比：响应完全相同，只有一条 turn，分数和追问计数只算一次，只有“模型返回后、保存前”会多一次模型调用。另外覆盖 pending 被别的请求抢占，以及锁失效时两个重试同时提交。内存存储和真实 MongoDB 各跑一遍 |
| `ReportWorkerCrashTest` | worker 拿到租约后退出：租约过期前其他 worker 不碰，过期后接管。收集完错题、发布前退出：重跑不重复写证据。worker 卡住期间被接管：醒来后不能覆盖结果。worker 运行中会话被删除：不留下报告和错题 |
| `AdaptiveChaosSimulationTest` | 用固定种子跑 200 场随机面试 |

随机模拟每一步随机做一件事：答题、重试、换内容重发、答过期的题号、刷新、时间快进、延期、手动结束。大约三分之一的请求会在随机位置崩溃，最后再跑一次报告 worker（一半概率中途崩溃）。每一步之后检查：

- 主问题列表、哈希和开始时间不变；
- 已答的主问题按顺序各计分一次，没有重复提交的 requestId；
- 追问不超过单题和全场上限，同一个缺口不追问两次；
- 同一个 requestId 每次拿到的响应都相同；
- 模型返回的每个结果，要么已经提交，要么还在 pending 里，要么能对应到一次“返回后、保存前”的崩溃或一次手动结束；
- 结束后一定有报告任务，最终只发布一次，错题证据不重复。

200 场大约 12 秒跑完，其中 156 场答完全部主问题，共 171 次追问，每个崩溃点都触发了 42～108 次。测试还会检查这些数字的下限，防止模拟悄悄退化成只走正常路径。失败时会打印种子和到出错为止的每一步，用 `-Dchaos.seed=N` 可以单独复现。我把“总是重新调用模型”这类错误故意写进业务代码试过，模拟和崩溃矩阵都能立刻抓到。

这次测出一个真问题：会话锁失效时，删除可能在报告 worker 收集错题的途中就完成了，而 worker 还拿着之前读到的会话继续写错题，已删除面试的回答片段就会留在错题集里。现在 worker 写每条错题之前，都会在错题锁里重新检查删除标记；删除清理用的也是同一把锁。

**还缺的**：

- 崩溃是用异常模拟的，不是真的杀进程，Redis 锁也是 mock 的，多实例真实抢锁没有在自动化测试里跑；
- 删除和报告 worker 在锁失效时还剩一个很窄的窗口：worker 检查完删除标记、还没写入错题时，删除恰好完成清理。要彻底关掉，需要删除流程在清理结束后再复查一次。

## 2. 本地端到端

用真实前端、真实模型和本地独立的数据库跑过以下场景（账号和简历都是合成的）：

| 场景 | 结果 |
| --- | --- |
| 30 分钟，正常答题 | 10 道主问题 + 3 次 RAG 追问；主问题全程不变；刷新后恢复；自动结束；面经展示和导出正常 |
| 20 分钟，真实慢答 | 实际等满 20 分钟。超时后显示可以继续或延期；10 道主问题答完，0 次追问，每轮原因都是 `TARGET_TIME_EXCEEDED` |
| 45 分钟，HTTP 接口 | 完整流程通过 |
| 手动结束 + 报告恢复 | 把报告租约手动改成过期后，定时 worker 能接管；同时启动两个实例抢同一个任务，只领取一次，报告一致，错题不重复 |
| 删除 | 从页面删除后，Mongo、MySQL、Redis 里的派生数据全部清零；重复删除幂等；他人无法删除 |
| 旧客户端 | 不调用新的 policy 接口时，原有流程（上传、出题、答题、结束、恢复）不受影响 |

过程中发现并修掉的问题：

- 刷新后题目还没恢复，输入框就已经可以输入 → 改成题目恢复完之前禁止输入；
- 删除时 Redis 扫描抛 `NoSuchMethodError` → Redisson core 和 Spring 适配器版本不一致，统一到 3.27.2；
- 页面并发读取时会话锁立即失败 → 自适应会话的锁改成最多等待 2 秒；
- 旧的错题唯一索引没有包含范围字段，不同范围的相同缺口会冲突 → 改用包含范围的稳定 `_id`，迁移脚本里移除旧索引。

还没覆盖：真实麦克风和摄像头、语音合成（本地没有配置讯飞 TTS 凭证）。

## 3. 模型评测

### 数据

数据集在 [docs/evals/](evals/)，都是合成回答，标签没有经过人工复核：

- `dev-60.json`：调试集，20 道题、60 条回答，调提示词时反复使用；
- `holdout-60.json`：验收集，同样 4 个主题下的 20 道新场景题，标签在调用模型前就提交了，之后不再修改；
- `smoke-6.json`：6 条冒烟用例。

每道题配 3 条回答，覆盖正确、部分正确、明确错误、没涉及和“不知道”等情况。

### 结果

模型为 Qwen3-Next-80B-A3B-Instruct（在讯飞工作流上运行），目录版本为 `java-starter-v3/v4`。

| 指标 | 结果 |
| --- | --- |
| 调试集严格通过（初版提示词） | 43 / 60 |
| 验收集严格通过 | **52 / 60** |
| 验收集目标评分点一致 | 67 / 75（缺失 0，重复 1） |
| “明确错误”识别 | TP 24 / FP 1 / FN 0，precision 96%，recall 100% |
| 检索：20 道题完整命中资料 | 14 / 20（v3）→ 19 / 20（v4，加了别名组） |
| 检索：无关问题、不支持的版本、不相关岗位 | 全部正确拒绝 |

“严格通过”的意思是：这条回答的每个目标评分点状态都和标签一致，并且没有重复或缺失。precision 和 recall 是相对于未复核的标签算的，不等于真实准确率。

### 8 条失败的分析

| 类型 | 条数 | 例子 |
| --- | --- | --- |
| 扩大考查范围 | 3 | 题目只问哈希碰撞，模型却要求回答 equals 的自反性和对称性 |
| 把“不知道”判成部分理解 | 2 | 回答说“不知道 equals 有什么问题”，被判为 PARTIAL |
| 未知实现被当成已知 | 2 | 题目问一个未说明实现的数据库，模型按 InnoDB 判对错（其中 1 条的标签本身有歧义） |
| 同一评分点给了两个状态 | 1 | 运行时会被降为 UNCERTAIN，评测按失败算 |

8 条里有 5 条的错误输出都是 `PARTIAL`：模型倾向于“要求更多”。这也是为什么设计上让 PARTIAL 产生的错题先进入“待确认”，而不是直接算作缺漏。

联调时还发现，模型写的解释经常夹带资料里没有的说法，比如 MySQL 那道题，它自己补了一段关于 gap lock 的解释。所以现在给用户看的反馈改由程序根据证据生成（见设计文档 5.3 节）。这能挡住编造的解释，但挡不住状态判错。

### 怎么跑

```bash
# 只校验数据集格式，不调用模型
python3 scripts/evaluate-grounded-workflow.py --dataset docs/evals/holdout-60.json

# 真实调用（会产生费用）：config 是包含 API_FLOW_ID / API_KEY / API_SECRET 的 env 文件，放在仓库外
python3 scripts/evaluate-grounded-workflow.py --dataset docs/evals/holdout-60.json \
  --config ~/grounded.env --output /tmp/holdout-results.json --generate --max-calls 60

python3 scripts/summarize-grounded-evaluation.py --dataset docs/evals/holdout-60.json \
  --results /tmp/holdout-results.json --output /tmp/holdout-summary.json
```

一次跑完 60 条大约消耗 7.7 万 token。脚本不会自动重试；输出文件已存在时会拒绝运行，避免重复花钱。
